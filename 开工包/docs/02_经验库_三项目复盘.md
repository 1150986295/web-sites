# 网页施工通用经验与模板 · 三项目复盘

> 整理日期：2026-11-24
> 来源项目：**墨缘**（豆包·大）、**竞墨**（WorkBuddy·大）、**专升本每日修炼**（WorkBuddy·小）
> 用途：**以后开新网页前先读这份**。第一部分看同类项目踩过什么坑，第二部分记通用规律，第四部分直接抄模板。
> 使用方式：新会话开场把这份文件发给 AI，说"按里面的模板和规矩来"。
> **出事急救**：人自己查独立的《症状速查表.md》（按现象找第一动作），再翻项目档案；AI 只记模板 J 里三条提炼。

## 〇、一句话总纲

> **小项目拼"克制"，大项目拼"地基"。而所有项目都死在同一个地方——轻信 AI 的自报、没有唯一判据、一个页一个改法。**

三个项目体量不同，但真正让人返工的坑高度重合：

| 反复出现的坑 | 在哪几个项目都中招 |
|---|---|
| **骨架选型决定手感上限，先天不足后期补不回** | 竞墨（划照片，最典型）、专升本（引擎先行才避开） |
| 信了"已修复/构建成功/本地测是好的"，实际没生效 | 墨缘、竞墨、专升本 |
| **"删了没报错"却全站打不开（静默失败）** | 墨缘（11-09 删请求头事故） |
| 没有唯一判据，靠感觉判断"改好没" | 墨缘、竞墨 |
| 视觉/样式没总纲，做一个改一个 | 专升本（最典型）、墨缘 |
| 数据只存本地，没备份 / 没权限分层 | 三个都有 |
| 图片不压、请求体过大，真机上炸 | 墨缘、竞墨 |
| 身份/鉴权混乱（多源、双表、401/403 误伤） | 墨缘（最惨）、竞墨（做对了） |
| 前端交互"点了没反应"（白屏/按钮被遮/上传无响应） | 墨缘 |
| 把"运营数据没填"误判成"代码 bug" | 墨缘 |

# 第一部分 · 三个项目分别踩的坑

## 一、墨缘（豆包平台 · 大项目 · 带后台的多页 Web App）

**性质**：书画协会作品征集平台，20 天工期，多页面 + 完整后台 + 身份认证 + 数据库。发布在豆包/秒哒平台。

### 发布与判据（最惨痛的一类）

• **"构建成功"不等于"发上去了"。** 唯一判据是 **CDN 目录名 = commit 完整 hash**，hash 没变就是没发布。曾靠"构建成功"提示误判多次。
• **发布前先弄清这次会带上哪些 commit**——rebase 曾一次带进 7 个主分支提交，自己却只知道"修了什么"。
• **主分支禁止 force push**；特性分支 rebase 后用 `--force-with-lease`，不用 `--force`。
• 靠主包**字节数 + md5**判断"这版到底改没改前端"——**要分开看两个信号**：字节数完全相同 → 体积没变；md5 不同 → 内容确实变过（哪怕一个字节）。**md5 是雪崩式摘要，差一个字节就整串全变，不存在"只差几处"这种可读信息**；想知道改了什么，必须拿两份文件 diff，不能从 md5 反推改动大小。

### 2026-11-09 全站打不开事故：删了一个"看起来没用"的请求头

> 这就是"改功能 → 发现要补功能 → 页面打不开"那次。用户记忆模糊，这里记全，因为它是最阴的一类故障——**静默失败**。

• **起因**：为了修一个 bug，删掉了请求头 `x-larkgw-suda-*`。它"看起来没用"——删完**代码不报错、构建成功、资源全返回 200**。
• **真相**：平台靠这个头注入 `appId`。头没了 → 入口 HTML 注入出 `appId=""` → 前端判定"应用不存在"，**全站打不开**。
• **最阴的地方（分层验证的教训）**：当时 L0 传输层全是 200（CLI 显示 finished、JS/CSS 都能下载），但 L2 渲染层是"页面不存在"、L3 运行时 `appId=""`。**只看"资源 200"会得出"是好的"这种完全错误的结论。**
• **事故前的原话信号**："这个应该不影响别的功能"——后来这句话被列进"听到就立刻叫停"清单。
• **处置教训**：先回退后查因。当时先分析再回退，用户在外面干等很久。

**由此立下两条通用规矩（已沉淀到发版约束卡）：**

1. **影响面四问**（删除/重命名任何请求头、字段、环境变量、路由、策略前必答）：
   - 除了我，还有谁在读它？（平台注入层、框架、其他模块、外部脚本都算）
   - 删掉它，谁会**静默失败**——不报错、但行为变了？
   - 能不能**先加后删**（分两步）？
   - 我怎么在 5 分钟内**证明**没人用？（全仓搜引用 + 查平台行为 + 测试环境单独删一次观察，三者缺一视为未证明）
2. **"不报错"不等于"没人用"**——这是静默失败最贵的地方。以及发版后**分层验证**：L0 传输→L1 文档→L2 渲染→L3 运行时→L4 业务，必须"浏览器打开亲眼看见内容+截图"，状态码不算数。

### 认证与权限（技术债高发区）

• **401 和 403 必须区别对待**：401 → 清空 localStorage 并强制登出；403 → 不清空。曾因 `badges?studentId=` 带合法 token 仍返回 401，导致"登录后点我的被强制登出"的 P0。
• `suda-csrf-token` cookie 只防跨站，**不是身份凭证**；光有 cookie 不算登录，必须带 Bearer token。
• **别"顺手写成统一守卫"**：badges 接口兼着匿名公开的徽章墙，手写校验是有意为之，套硬守卫会把匿名请求也打成 401。
• **删字段要治本**：让后端从 token 取 `studentName`，而不是前端补字段——前端补等于让客户端可伪造姓名。

### 身份失效循环 + 管理员/学生身份名单混乱（最大的 P0 区）

> 这是墨缘最纠缠的一类坑：一个"鉴权小改动"能引发"所有人一操作就被强制登出"的连环故障，且管理员和学生各有不同的触发原因。

• **别让 401 和 403 一起触发"身份失效"**：旧代码写的是 `status === 401 || status === 403` 就广播 auth-lost——结果**任何 403 都清空登录态、弹"身份失效，请重新登录"**（写成 `!==` 的反向判断则一个都不拦，同样错，判断方向必须以实测为准）。而登录成功时会重置一次性标志位，导致**每次重新登录后遇到的第一个 403 又触发一次**，形成可重复、不自愈的死循环。修法：只认 401，403 绝不登出。
• **"被强制登出"要分清环境再动手**：用户报"所有账号一操作就掉线"，实测正式地址登录、进 4 个后台 tab、首页↔作品往返，全程 0 个 401/403——问题在**豆包对话框预览（构建 dev）和正式版不是一套登录环境**。先问"测的是哪个环境、版本号对不对"，别急着改代码。**第一优先是分清环境，不是派活排查。**
• **一个字段两套表，改密必失败**：`admins` 和 `class_students` 双表密码哈希不同步——**登录查一张、改密写另一张**，导致改密码返回 403"当前密码不正确"，但同一个密码却能登录。身份数据**绝不能散在两张表里**。
• **身份判断别用前端硬编码/双身份源**：曾出现"已登录已加入仍显示『我要加入』"（按钮无条件渲染、没套状态判断）；还有 localStorage 只有学生 token 没有管理员 token、靠 cookie 会话撑着的历史悬案。**身份以服务端为准，前端只做展示。**
• **名单/权限的错，很多是"前端多套了一层 isAdmin"**：接口本就返回全量名单，前端却套 `isAdmin` 让普通会员看不到打卡名单；"学生管理页只剩删除"是操作列渲染被删减。**先查接口返回，再看前端是不是自己把数据藏了。**
• **两个入口跳同一个页面**："开始打卡"和"硬笔书法"都跳 `/hard-pen`，是三元表达式第一个分支写错。这类"页面与入口不对应"要逐个入口点验，不能只看页面在不在。

### 判读规则（被坑两次，写死成规则）

• **自检报 error ≠ 系统故障**：后台那 12 项红黄灯反映的是**数据完整度**，是一份"运营待办清单"，不是 bug 列表。代码错的标志是接口 500 / 白屏 / 点了没反应 / 数据串位；人没填的标志是列表能打开、字段空着。
• **别把"最近才注意到"当"最近才加的"**：扣子测评称"这版刚加了备份/自检"，据此推出 P0——前提是假的（建站起就有），前提假 → 后面再精确的观测因果链也是断的。
• **报 404 先怀疑自己的路径**：曾把 `/api/calligraphy/all-works` 记成 `/api/all-works`，误以为路由被删。前端 bundle 里能 grep 出全部真实路径。
• **实测反证，不要"补功能"**：曾以为作品墙缺收藏按钮，实测 `lucide-star=0` 证明本来就没有（收藏只在详情页），补了等于新增功能、引入风险。
• **"为修一个 bug 在生产开一个新口子"**：为了让登录 500 的错误原文显示出来，给异常过滤器加了 `rawMessage`，结果**把整条 SQL 和表结构返回给了前端**——调试代码上了生产。教训：生产只返回 `{code,message,traceId}`，SQL 原文只写服务端日志，开发/预览环境才保留详细错误。
• **接口缺参别返回 500**：多个接口不传参数直接 500 还吐 SQL，应在入口做必填校验、返回 400 + 中文提示。

### 性能与图片

• CDN 图片压缩参数**必须编码形式**：`?x-tos-process=image%2Fresize%2Cw_800`，裸写 `image/resize,w_800` 慢一倍。
• 列表用缩略图 + `loading="lazy"` + `decoding="async"`，**详情页/放大/下载继续用原图**。实测 455→88KB（-81%），加载 1.0-1.8s→0.3-0.4s。
• 等比缩放，**不动 quality**。

### 白屏、闪屏与"点了没反应"（前端交互层的高频坑）

• **冷启动白屏 2.17s（4G）/ 4.25s（3G）**：四条根因——①入口 HTML 是空壳（只有一个 `<div id="root">`，0 个 style）；②遮罩和首页**同帧挂载**，没起到"先盖住"的作用；③云层与底色色差仅 11 阶，数学上有云、肉眼看不见；④`sessionStorage` 记忆导致刷新不播动画。压缩后仍有 0.86s。**教训：入口 HTML 要有底色、遮罩要先于内容挂载。**
• **"选完图零请求、零报错、连占位都没有"**：根因是 `input.files` 是 **live FileList**，`e.target.value=''` 会把它清空，而代码存的是同一个引用，紧接着 `length===0` 成立直接 return。同一个 bug 在三个入口复制了三遍。修法：先 `Array.from(e.target.files)` 拷贝再清空。**对比定位的关键**："更换封面"是好的，因为它取的是单个 File 对象、不受 value 清空影响。
• **"保存点不到，其实命中底部 tab"**：编辑面板高度没扣掉底部导航，按钮落在可视区外（y=843、屏高844、底栏56）。移动端弹层/面板要算上底部 tab 高度。
• **装饰层 z-index 高于交互层**："我的"页按钮被水印遮挡；右侧悬浮球重复渲染遮挡内容。**装饰永远不能盖住可点元素。**
• **"点确认删除"弹窗关了但零请求**：只关了弹窗、没调删除接口，刷新还在。**关窗≠执行**，要验后端数据真的变了。
• **自动化脚本命中不可见按钮导致误判**："改图保存不生效"是脚本用了"页面上最后一个含『保存』的按钮"，命中的是隐藏候选元素；"共X张"读的是编辑区文案不是列表长度。**脚本误判要复测推翻，别据此写根因**（这条最后撤回留档）。
• **58 个元素带 `touch-action:none`** → 后台成员列表手指起滑无反应，只能在信息框外滑。应改 `pan-y`。移动端别乱禁触摸。

### 验收视角

• **别用 admin 视图验视觉效果**：admin 默认在"编辑态"，看到的是平铺管理列表；要关掉右上角编辑开关切到"浏览态"才是用户看到的 3D 轮播。曾因此误判"功能没上线"。

### 成本（豆包按 token 计费的特殊教训）

• **同类改动合并发**：三处"加一个 URL 参数"分三次发，烧了 285 积分，代码各 1 行——贵在每次新任务都要重读整个代码库。合并发能压到个位数。
• **按输出量选模型，不按任务类型选**：纯样式/CSS → 最便宜的 Flash；改逻辑/状态/接口 → 主力模型；判影响面/长上下文 → 贵模型。
• **验收交给本地巡检脚本**（如 `/workspace/tools/墨缘巡检.py`），别让 AI 自己 build + 截图，每轮多烧一次。
• **省积分提示词反而费积分**："让模型自己找最省办法"是反效果（它会花推理去想怎么省）。要用明确的短指令：不展示推理、严格按清单改、验证只做列出的项、卡住就停。

## 二、竞墨（WorkBuddy 平台 · 大项目 · 单文件 HTML + 后台接口）

**性质**：书法比赛征集系统，报名→投稿→后台评分→上墙→导出全链路。单文件 HTML 前端 + 后台接口，平台内已有真实数据（65 报名 / 63 交卷），**测试时严禁碰 clearall / reset / remove**。

### 最大的坑：骨架先天不是墨缘那种 → 切页像"划照片"（花大力气才补回来）

> 这是竞墨**排第一的教训**，比大图上传还根本——因为它决定了整个项目的"手感上限"。

1. **起因**：竞墨一开始的骨架就不是墨缘（豆包多页 App）那种带原生页面切换架构的形态，而是单文件 HTML。结果就是**页面切换没有过渡，像划照片一样生硬**——点一下 tab，整屏内容直接跳过来，没有墨缘那种丝滑切场。用户当时的原话诉求："它后面可以像墨缘一样拥有丝滑的切场动效吗？"
2. **代价**：这个"手感"是**骨架层决定的，不是后期加个 CSS 动画能糊弄过去的**。后来专门做了一套"统一入场引擎"才补回来：所有切页走同一套、只动 `opacity/transform`、幂等固化、级联延迟、回弹曲线、200ms 退场——等于在大项目后期回头补地基。
3. **残酷的对比结论**：因为骨架不同，竞墨在这项上**对比墨缘天生没有优势**，补救能做到"不生硬"，但要完全达到墨缘那种原生丝滑，成本很高。**架构选型的债，最后是体验来还。**
4. **教训（写进通用规律）**：**切场/导航/动效这类"全局手感机制"，必须在骨架阶段就定死**。不要想着"先能用，动效以后再说"——后期补是补不回原生手感的，而且会牵动所有页面。

### 鉴权设计（做对了的部分，可作为范本）

1. **身份字段只定一个**：登录返回 `{token, who, recovered}`，身份只有 `who`，绝不并存 `isAdmin` 这种第二身份源（两个源必然不同步）。
2. **localStorage 双键成对**：`lt_admin`（令牌）+ `lt_who`（身份），注释写明"成对写、成对清；401 统一清空整套"。
3. **前端藏 tab + 后端守卫双保险**：未登录时管理入口 `display:none`，同时每个 `/api/admin/*` 独立检查 token——只做一层都会被绕过。
4. **首登改密不死锁**：识别组织者 → 自动弹初始密码改密框；但 `needChange=true` 的账号只 toast 不自动弹（遗留差距）。
5. **学生登记 ≠ 登录**：登记是姓名+学号+班级+手机+口令，设备指纹一机一次；登录是另一套。别混。

### P0：大图多张上传必炸（最有价值的一条）

6. **请求体 ≥ 约 38MB 时代理层直接断连**（500 ECONNRESET）。手机照片 3~8MB，一次传 4 张大图就超，而前端只显示"网络异常，请检查网络后重试"——学生重试一百次也不会成功，现场会失控。
   - **修法**：上传前 canvas 压缩（长边 >1600px 等比缩到 1600px，转 JPEG 质量 80，单张压到 1MB 内）；提交前估算 base64 总量，>25MB 就拦下并提示"图片过大，请减少张数"；错误提示要**区分**"体积过大"和"网络异常"。
     > 口径说明：1600/1MB 是本次复盘的**当时参数**；模板 B 骨架与 `01_施工规格书` §1.5 的现行口径是 **长边 1080 / 压缩后 300KB**（更省流量、移动端够用）。两者不要混用，按项目阶段选一套并写进验收单。
   - 7.8MB 原图 → 8KB 缩略图（-99.9%），上传速度和成功率都翻倍。
7. **并发退化**：60 并发刷墙，60/60 成功但中位 4.6s、P95 5.3s（单发只要 0.1~0.5s）。压缩后单请求变小会明显缓解；流程上分组上传避免集体齐发。

### 动效（先天不足后的补救方案，思路可跨项目复用）

8. **统一入场引擎（就是上面"划照片"坑的补救）**：所有页面切换走同一套，只许 `opacity/transform`，播一次即固化（`ENTER_SEEN` 幂等标记）；用 `getAnimations()` 检测复播；禁止用 display/height/top/width 做动画。**记住这是"亡羊补牢"——新项目应该在骨架阶段就把它内建进去，而不是事后补。**
9. **角色动画的朝向要统一由一个变量控制**（如 `scaleX(--dir)`），左右方向都要验。曾出现"身体朝前、方向朝后跳"的怪异画面，就是因为朝向散落在多处。

### 测试纪律

10. **压测后必须还原数据**：测试作品/报名走正常删除通道清掉，复核真实数据原样（65/63、报名恢复 N 人、作品墙归零）。
11. **危险操作要二次确认**：删除报名需管理密码，clearall 需输入 `CLEAR`——测试时绝不碰。
12. **声称的限流要实测**：`/api/recover` 号称"5 次/分钟"，实测 20 次无 429 → 限流根本没生效。**不要信注释里的数字。**

## 三、专升本每日修炼（WorkBuddy 平台 · 小项目 · 纯单文件 HTML + localStorage）

**性质**：个人刷题备考站，5 页（今日/练习/知识/错题/我的），无后台、无账号、localStorage 存全部数据，只私发一两人用。

### 定位决策（小项目的核心是"克制"）

1. **不要为了一两个人上名单登录/后台**：那是把"能直接发的链接"升级成"要长期维护的系统"。而且**挡不住转发**——对方把链接往群里一丢照样进。私发链接 + 叮嘱即可。想留底就给每人发带不同随机参数的链接，外流了能知道从谁那儿出去。
2. **数据只存 localStorage 是真实风险**：清缓存或换手机 = 全部记录没了。对小项目，加一层**导出/导入 JSON** 就够了（几行代码），不要上云端同步（要账号后台，与"一两人私用"冲突）。
3. **单文件 HTML 也能做复杂功能**：记忆引擎（SM-2 简化：1→2→4→7→15→30 天，答错重置，按考点聚类错题）、计划引擎（以日期字符串为种子，同日刷新计划不变）都能纯前端实现。

### 一个页一个坑 → 立"总纲"（本项目最大教训）

4. **视觉/排版没有总纲，就会"做一个改一个"**：科目标签颜色反复改（实心绿太跳→朱砂撞按钮→蓝绿太像→最终黛蓝/紫檀/赭黄）；红字用 `nowrap` 撑出屏幕；字号 12~14px 费眼；公式是裸 LaTeX 源码 `$\frac{}{}$`。
   - **根治**：写一份 **R3.8 全站排版总纲**，优先级高于所有零散补丁，任何新页面动手前先过总纲（设计令牌、容器换行、通用组件、公式渲染、字号层级、自检清单）。
5. **强调色只能有一个**：朱砂红是全站唯一最高强调色，专留给"提交答案"这类主操作。科目标签也用朱砂，会稀释按钮、还带出"错误/警告"歧义。配色要在色环上**拉开色相**（蓝绿只差 60° 小标签上就糊成一类）。
6. **字号别低于 16px 正文**：手机上要逐字读的页面，12~14px 最费眼。辅助标签 ≥13px，行高 1.75。
7. **英文单词断词**：中文断行规则套到英文上会把 `abstract` 拆成 `ab`+`stract`。每个单词用 `<span style="display:inline-block;white-space:nowrap">` 包起来，作为整词换行。
8. **公式必须有渲染层**：题库里是 LaTeX，必须有 KaTeX 渲染 + 离线降级（断网转 Unicode 符号），不能当纯文本输出。
9. **跳转放最后**：知识卡先讲透知识（定义→公式→题型识别→步骤→易错→例题），"相关题目 N 道"的跳转永远在最后一行，不得占主视觉。

### 交互与数据口径

10. **"翻面"和"跳题"不能糊成一个动作**：用户想翻面看要点，却被送去做题——两个动作必须分开。
11. **进度口径必须唯一**：曾同屏出现"0/21 今日总进度""完成 1/3 组""已完成 0 段""0/4 段完成"四个数字三个分母，用户不知道信哪个。**只保留一个分母，其余全删。**
12. **倒计时日期要持久化**：刷新后变"距考试 -- 天"，因为日期没存 localStorage / 首屏读取时机错。存本地 + 同步读取 + 解析失败给默认值，不许裸 `--`。
13. **同一屏数据不能自相矛盾**：上写"到期复习 0 项"下写"14 项"、上写"新考点 0 个"下列了 3 个——两处组件各读各的数据源。统一取数。
14. **脏数据会毁可信度**：解析里写"故选 C"但题目根本没有选项；参考答案写成"the; /"。题库内容要单独核验，不能只验功能。

# 第二部分 · 通用经验（提炼成可执行的规律）

## A. 开工前

- **先写一页纸**：谁用、每周来干的一件事、第一版必须有、第一版不要、三个月后只剩一个功能留哪个。写不出来就别开工——交给 AI 只会得到"什么都有、什么都不顺"。
- **先定体量**：小项目（个人用/一两人）走单文件 + localStorage，**不上后台不上登录**；大项目（多人/要数据/要权限）才上后台 + 鉴权 + 数据库。体量选错，后面全是白干。

## B. 骨架与鉴权

- 五阶段不跳：**骨架 → 地基 → 内容 → 美化 → 试用**。地基（权限、备份、错误提示、版本号）不产生界面变化，最容易被跳过，也最容易三个月后炸。
- **骨架阶段就要定死"全局手感机制"——页面切换/导航/动效引擎。** 竞墨的教训：骨架不是墨缘那种架构 → 切页像划照片，后期花大力气补统一入场引擎，仍难完全追平原生丝滑。**这是架构选型的债，最后用体验来还**；别信"先能用，动效以后再说"。
- 选骨架时直接问一句：**它原生支持丝滑切场吗？** 如果不支持，要么一开始就接受"手感次一档"并明确取舍，要么换架构——不要事后才发现。
- 身份字段**只定一个源**；令牌与身份双键成对写、成对清；401 统一清空整套。
- 前端藏入口 + 后端守卫**双保险**；401 登出 / 403 不登出要分清。**403 绝不能触发登出**——墨缘就是 401/403 一起广播"身份失效"，形成"重登→第一个403→又登出"的死循环。
- **身份数据只存一张表**：墨缘的 `admins` 和 `class_students` 双表哈希不同步，登录查一张、改密写另一张 → 改密永远失败。身份别散在两处。
- **名单/权限显示异常，先查接口返回**：很多是前端自己多套了一层 `isAdmin` 把数据藏了，接口本来就是全量。
- **页面与入口一一对应要逐个点验**：墨缘两个按钮跳同一页面、已加入还显示"我要加入"，都是前端没套状态判断。
- 首登改密的流程要能走通，别把用户锁死在"必须改密"的死锁里。
- 删除/清空类操作要二次确认（管理密码 / 输入特定词）。
- **报"全员掉线"先分清环境**：豆包/编辑器预览（dev）和正式版往往不是一套登录环境。先问版本号、测的是哪个环境，别急着改代码。

## C. 数据层

- **唯一判据思维**：发布看 commit hash，不看"构建成功"；功能上线看实测接口/页面，不看自报。
- 数据存本地就要有**导出/导入**兜底；存云端就要有备份策略。
- 以日期字符串为随机种子，保证"同日刷新计划不变"。
- 内容脏数据单独核验，功能对不代表内容对。

## D. 性能与图片

- 列表一律缩略图 + 懒加载，详情用原图；CDN 参数要编码形式。
- **上传前必压缩**：前端 canvas 压到长边 1600px / 单张 <1MB（历史值）；**现行模板口径 1080 / 300KB**，见 `01_施工规格书` §1.5；提交前估算总量拦截超限；错误提示区分"体积大"和"网络差"。38MB 是实测的代理断连阈值。
- 声称的限流/上限要实测，不信注释。

## E. 视觉与排版

- **先立总纲再写页面**（见第四部分模板 E）。设计令牌全变量化；容器 `box-sizing`+自动换行兜底；`nowrap` 只许用于单个英文单词；强调色唯一；正文 ≥16px；公式要渲染。
- 配色在色环上拉开色相，别让两种小标签糊成一类。
- 视觉验收用**普通用户视角**，别用 admin 编辑态。

## E2. 前端交互高频坑（"点了没反应"类，最容易被漏测）

- **入口 HTML 要有底色、遮罩先于内容挂载**：否则手机上冷启动盯 2~4 秒白屏；装饰层对比度太低等于没有。
- **`input.files` 是 live FileList**：存引用后 `value=''` 会把它清空，导致"选完图零请求零报错"。先 `Array.from()` 拷贝再清空。同类 bug 常被复制到多个入口，修一处要全线排查。
- **移动端面板高度要扣掉底部 tab**：否则"保存"按钮落在可视区外，点它其实命中底部导航。
- **装饰层（水印/悬浮球）不能盖住可点元素**：z-index 分层要验。
- **"关窗≠执行"**：确认弹窗关闭后要验后端数据真的变了（接口请求发出、刷新后状态改变）。
- **别用自动化脚本的"最后一个某文字按钮"定位元素**：会命中隐藏候选导致误判；误判要复测推翻再写根因。
- **移动端别乱用 `touch-action:none`**：会让列表滑不动，用 `pan-y`。

## F. 动效

- 统一引擎：只 `opacity/transform`，幂等标记，播一次固化，`getAnimations()` 检测复播，禁止 display/height/width 动画。
- 进度条宽度是 layout 变化，入场时直接呈现最终宽度，不要逐帧 animate width。
- 角色动画朝向由单一变量控制，左右方向都验。

## G. 验收（最重要）

- **别信自报**："已修复""本地测是好的""发布一下才能看日志"——一律要它在**预览里**测、把错误原文露出来。
- 自己点通关键动作，每轮发布后手机过 5 个关键路径。
- **证伪思维**：看到"缺某功能"先实测确认它本来是不是就没有，别急着补。
- 同一问题改 3 轮还不好 → 回退重新描述，别继续猜。
- 把判读规则**写进文件**（如墨缘的"自检 error 是运营待办不是 bug"），不靠记忆。

## H. 成本（用 AI 改代码时）

- 同类改动**合并一次发**，别切碎（每次新任务都要重读代码库）。
- 机械活（加参数/改文案/换色）用最便宜的模型；判风险/大上下文用贵模型；别中途换模型。
- 验收用本地脚本，别让 AI 反复 build + 截图。
- 指令要明确具体，别用"自己找最省办法"这种会诱发过度推理的话。

## I. 删除与发布安全（防"静默失败"）

- **"不报错"不等于"没人用"**：删掉一段代码/请求头/字段后不报错、构建成功、资源全 200，也可能被平台或别的模块悄悄依赖，一删全站崩。
- **删除/重命名前必答影响面四问**：还有谁在读？删了谁会静默失败？能否先加后删？怎么在 5 分钟内证明没人用（全仓搜+查文档+测试环境单独删一次）。
- **分层验证，别只看 200**：L0 传输（200）→L1 文档（HTML 对）→L2 渲染（浏览器看见内容）→L3 运行时（关键变量正确、无 console error）→L4 业务（写入读回）。**状态码 200 只证明第一层。**
- **出事第一动作是回退，不是查因**；回退目标=上一个已知良好版本；恢复后再分析。
- **线上正坏着时禁止顺手优化**——只回退或等指令，别给下次故障埋变量。
- **听到"这个应该不影响别的功能""接口都 200 应该是好的"立刻叫停**——这是事故前的原话信号。

# 第三部分 · 大项目 vs 小项目：怎么选架构

| 维度 | 小项目（专升本） | 大项目（墨缘 / 竞墨） |
|---|---|---|
| 典型场景 | 个人用、一两人私发 | 多人报名投稿、要统计和权限 |
| 前端形态 | 单文件 HTML | 多页 Web App / 单文件 + 后台接口 |
| **骨架选型（决定手感上限）** | 单文件也能丝滑，但**切场机制要在骨架里就内建** | **先问"原生支持丝滑切场吗"**——竞墨选错骨架→像划照片，后期补引擎仍追不平墨缘 |
| 数据 | localStorage + 导出 JSON | 数据库 + 服务端接口 |
| 登录 | **不要**，私发链接即可 | 必须，身份单一源 + 双保险守卫 |
| 备份 | 导出/导入 JSON | 服务端备份 + 发布纪律 |
| 性能重点 | 基本不用管 | 图片压缩、上传体积、并发 |
| 动效 | 统一引擎骨架期就内建 | 统一引擎 + 朝向变量 + 幂等；**后期补=还架构债** |
| 主要风险 | 数据丢失、样式失控、脏数据 | 权限漏洞、发布误判、大图上传、测试污染真实数据 |
| 施工节奏 | 快速迭代，但先立总纲 | 五阶段不跳，地基先行 |

**判断口诀**：
- 要不要登录？—— 超过"几个熟人私用"就要，否则不要。
- 要不要后台？—— 需要跨设备同步、多人权限、数据统计才要。
- 要不要总纲？—— **永远要**，哪怕只有一个页面。这是"做一个改一个"和"一次立规"的分水岭。

# 第四部分 · 可复用模板（直接抄）

## 模板 A · 开工一页纸

```
项目名：
谁用：（具体到人/角色）
他们每周来这儿干的一件事：
第一版必须有：（≤3 条）
第一版不要：（明确列出，防止 AI 加戏）
体量：□ 小（单文件+localStorage）  □ 大（后台+鉴权+数据库）
三个月后如果只剩一个功能，留哪个：
唯一判据：（发布看什么？功能上线看什么？）
```

## 模板 B · 提需求五行

```
【改什么】一句话说清
【在哪】哪个页面、哪个按钮
【改成什么样】具体行为，不要形容词（"好看一点"不合格）
【怎么算成功】我点几下、看到什么
【不要动】列出绝对不能碰的模块（动效/计划/数据/其他页面）
```

反面例子："把页面优化一下""感觉很乱"——这类话会让它一次改五个文件。

## 模板 C · 施工提示词（R 编号制）

```
### 提示词 R<N> · <一句话标题>（模型 <档位>；<日期>，<触发原因>）

> 【问题】用户原话 + 截图实证，写清现象，不写"感觉"
> 【根因】定位到具体机制（不要停在"样式坏了"）
> 【改法】分点，写到能直接抄的代码/CSS 级别
> 【红线】不许碰什么（列具体模块名）
> 【验收】点几下看到什么 + 报告计算样式/接口返回值
```

**规矩**：一条需求一个 R 编号；复杂的用 R3.1/R3.2 递增；**总纲类（如 R3.8）优先级最高，写明"其它条目与本节冲突以本节为准"**。

## 模板 D · 验收清单

```
□ 关键动作自己点通（不是听它说"已修复"）
□ 预览里测，不是"本地测是好的"
□ 手机窄屏无文字/红字/公式溢出
□ 发布后判据确认（commit hash 变了 / 接口返回对了）
□ 无 4xx/5xx、console 无错
□ 数据串位/自相矛盾检查（多个进度口径是否唯一）
□ 测试痕迹清理，真实数据原样
□ 每做完 3-5 条导一次备份、记版本号
```

## 模板 E · 全站排版总纲（每个项目都该有一份）

```
# 全站排版总纲（优先级高于所有零散补丁）

1. 设计令牌：:root 里定义颜色/字号/间距/圆角/阴影，组件只引用变量，不写死值
2. 容器与换行：*{box-sizing:border-box}；文本容器 max-width:100% + overflow-wrap:break-word；
   nowrap 只许用于单个英文单词/数字
3. 通用组件：警示条/按钮/标签/卡片/提示条统一 class，禁止浏览器默认样式露出
4. 强调色唯一：主操作专用，标签/装饰不许抢
5. 公式渲染：KaTeX + 离线降级，页面不得出现裸 LaTeX
6. 字号层级：标题 20 / 正文 16 / 辅助 ≥13，行高 1.75
7. 自检清单：每页上线前逐条过（见模板 D）
```

## 模板 F · 发布纪律

```
1. 发布生效唯一判据：commit hash / 版本号变化，不信"构建成功"
2. 发布前弄清这次会带哪些 commit
3. 主分支禁 force push，特性分支用 --force-with-lease
4. 删除/重命名任何头/字段/路由/策略前，先答"影响面四问"，答不出不许删
5. 发版后分层验证：L0传输→L1文档→L2渲染→L3运行时→L4业务，"浏览器看见内容+截图"才算数，200 不算
6. 出事第一动作是回退（到上一个已知良好版本），不是查因；故障期禁止顺手优化
7. 发布前自己点通，发布后手机过 5 个关键动作
8. 每 3-5 条改动导一次备份、记版本号
```

## 模板 G · 收工三行（每次会话结束写）

```
日期：
这一版能做什么：（三条以内）
已知没做/没验：（一条一行）
```

下次开工先看这三行，就不会"完全搞混了"。

## 模板 H · 微文案表（M8 落地｜错误/状态提示只准从这里抄，AI 不许自己发挥）

**规矩**：任何提示文案固定三段式——**发生了什么 + 为什么 + 现在怎么办**；按钮用动词；禁止"请稍后重试""网络异常""操作失败"这类零信息话。

| 场景 | 固定文案（直接抄） |
| --- | --- |
| 图片体积过大 | 「图片太大了（约 X MB），一次最多传 Y MB。请先删掉几张，或换小一点的图再试。」 |

## 模板 I · 发布台账 RELEASES.md（M2 落地｜防"线上旧产物 / 仓库新源码"分裂）

每个项目根目录建一个 `RELEASES.md`，**每次发布后追加一行**，新在上：

```
| 日期 | 改了什么 | 线上文件指纹（字节数+md5前8位） | 对应源码提交/备份文件名 | 谁验的、怎么验的 |
|---|---|---|---|---|
| 2026-11-24 | R3.9 错误红点 | 152,340 字节 / a1b2c3d4 | backup_20261124_2130.html | 本人：断网点提交→红点→刷新仍在 |
```

**三条规矩**：
1. **发布前先存线上版**（备份文件名写进台账），改完发布再补一行——顺序不能反。
2. 回退 = 按台账找到上一个"已验收"行，取它的备份文件重传，**不看别的**。
3. 台账里找不到对应备份的行，只能判定**"这次发布没有可回溯记录"**，必须补齐证据才能继续发下一版；**不能据此反推"上线没发生"或"线上版本没变"**——记录缺失与事实缺失是两回事。

## 模板 J · 症状速查表（M12 落地｜独立存放，给用户自己查，不随本文档喂 AI——省积分）

**不放在本文档里**（本档是开工喂给 AI 的，症状表是出事时人自己查的，混在一起每次多读一屏字）。完整表格独立存于 `症状速查表.md`（11 行"症状 → 第一动作 → 高频根因"）。

给 AI 只需记住三条提炼：
1. 全站打不开 → **先回退再查因**（最大嫌疑：动了平台注入的东西）
2. 白屏/点了没反应 → 先取证（红点、console、截图），别凭感觉改
3. 提交"成功"数据没变 → 直接查数据源，别信界面

## 模板 K · 通用巡检（M1 落地｜证据制，结论看文件不看转述）

**工具**：`/workspace/tools/网页巡检.py`（已在埋坑测试页上实测：console 报错、资源 404、横向溢出、裸 `\frac` 禁词、错误红点历史全部抓到）。

**用法**（每站一份配置 JSON，已建好骨架：`巡检配置_专升本.json` / `巡检配置_竞墨.json`，把线上链接填进去即可）：

```
python3 /workspace/tools/网页巡检.py --config /workspace/tools/巡检配置_专升本.json
```

**铁律**：
1. **结论只在产物文件里**——`巡检结果_<站>_<时间>/` 下的 PNG 截图 + results.json + index.md。**AI 转述的"X 项过"不算数**，你自己开 index.md 看 FAIL/WARN 表。
2. 退出码 0=全过、1=有 FAIL，可用于自动拦截。
3. 固定检查项不需要配置自动跑：HTTP 状态/重定向链、标题断言、入口底色（防白屏）、console 报错（滤噪声）、资源 4xx/5xx、**横向溢出检测**、禁词扫描（裸 LaTeX/零信息文案）、**错误红点 localStorage 读取**（与 R3.9 打通）、动作回放每步截图。
4. 每站把"5 个关键动作"写进配置的 `actions`（点哪、等哪、截哪），巡检就替你把验收路径回放一遍。
5. 噪声（如字体 CDN 的 octet-stream）写进配置 `noise`，不算错——**但往 noise 里加东西前要说明理由，不许拿来掩盖真问题**。

# 五、踩坑速查红线（打印贴墙上）

1. **"构建成功/已修复/本地测是好的"一律不算数** —— 要唯一判据 + 预览实测。
2. **发布看 hash，不看提示。**
3. **骨架定手感上限——切场/导航/动效引擎在骨架期就定死，别信"以后再补"（竞墨划照片之痛）。**
4. **身份只有一个源，401/403 分清，双键成对清。**
5. **上传前必压缩，38MB 是断连阈值。**
6. **删东西前答影响面四问——"不报错"不等于"没人用"（删请求头→全站打不开之痛）。**
7. **发版分层验证，200 只证明第一层；出事先回退后查因。**
8. **先立总纲再写页面，做一个改一个是万恶之源。**
9. **强调色唯一，配色拉开色相。**
10. **正文 ≥16px，英文单词整词换行，公式要渲染。**
11. **进度口径唯一，数据不自相矛盾。**
12. **自检报错先问"是代码错还是人没填"。**
13. **看到"缺功能"先实测证伪，别急着补。**
14. **测试不碰真实数据，压测后还原。**
15. **同类改动合并发，机械活用便宜模型，验收用脚本。**
16. **重要的事写进文件，不靠记忆。**
17. **一小时交 3 个以上版本 → 停；开始"修上一个修复造成的问题" → 回退。**

# 六、AI 三头会审机制（2026-11-25 增补，模板方案全程实战验证）

## 6.1 分工格局（实测有效）

| 审查方 | 擅长抓的错 | 实战战绩 |
|---|---|---|
| 豆包 | **事实层**：下载方式、文件真伪、行为 bug | 抓到"首账号不标管理员→后台永远进不去"真坑；也编造过 RELEASES.md、误判 zip 为空 |
| 扣子 | **方法论层**：经验过拟合、缺样例、文档膨胀 | 抓到"实测值照抄风险"“视觉工序缺好坏对照"；也误报过"开场白重复两遍" |
| 主对话（执行者） | **实测把关**：每条外审意见逐条验证再采纳 | 多次驳回外审误判（zip 是满的、索引已修、开场白仅1处） |

## 6.2 会审规则（写死）

1. **外审意见一律实测再采纳，不照单全收**——两个外审都有误判史，也都有真贡献，价值在交叉验证。
2. **发外审前确认它拿到的是最新版本**——豆包曾基于修正前的旧快照误判"问题仍未修"（快照陷阱）。
3. **外审要能读到真内容**：发 `.app.workbuddy.host` 线上链接或直接发文件本体；资料库 html 链接会变成 12KB 平台壳，别发那种。
4. **采纳分两档**：文档级（改文档）vs 代码级（改模板）——代码级修改必须回归巡检全 PASS 才算过。
5. **审查结论也记账**：谁的误判、谁的真贡献都留痕，防止"上次说过的错下次再信一遍"。
